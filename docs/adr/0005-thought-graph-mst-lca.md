# ADR-0005. Граф мыслей: максимумное остовное дерево, BINUP LCA и reroot

- **Статус:** Accepted
- **Дата:** 2026-11-19
- **Модуль:** 4, [include/thought_graph.hpp](../../include/thought_graph.hpp)

## Контекст

Конвейеру нужен объяснимый «путь мысли» между корнем и стоком, а также
быстрые запросы о пути и его весах. Требования:

- детерминированное остовное дерево над тем же набором рёбер, что использует
  поток;
- запрос LCA и веса пути за `O(log N)` без рекурсии в горячем пути;
- возможность сменить корень (`reroot`) без пересборки рёбер;
- отдельно нужна верхняя оценка веса пути и истинный bottleneck (минимум).

## Решение

1. **Максимумное остовное дерево (Maximum Spanning Tree).**
   `Edge::operator<` сортирует по убыванию веса, затем Краскал с DSU
   (`find` с path compression) добавляет ребро в `adj_mst`, если оно соединяет
   разные компоненты; остальные рёбра попадают в `adj_horiz` (хорды).
   Несвязные компоненты дополнительно соединяются с вершиной `0` ребром веса 1.
2. **BINUP LCA.**
   Для каждого узла хранятся таблицы `up[u][i]`, `max_edge[u][i]`,
   `min_edge[u][i]` по `log_n = max(8, ⌈log₂ n⌉)`. `dfs_lca` заполняет их
   итеративно по слоям. `query_path_binup` возвращает LCA и **максимальный**
   вес на пути; `query_path_min_binup` — LCA и **минимальный** вес
   (истинный bottleneck).
3. **Динамический reroot.**
   `reroot(new_root)` меняет `current_root` и заново запускает `dfs_lca` от
   новой вершины.

## Обоснование

- **Почему максимумное дерево, а не минимумное.** Вес ребра — это
  пропускная способность/сила связи. Остовное дерево должно сохранять
  самые сильные связи, а не самые дешёвые; иначе объяснимый путь проходил бы
  по слабым рёбрам. Сортировка по убыванию — прямое выражение этого
  требования.
- **Почему Краскал + DSU.** Рёбер немного (96 в подграфе), сортировка дешёвая,
  а DSU даёт почти линейную проверку циклов. Альтернатива Прима требует
  приоритетной очереди и хуже выражает «взять самые сильные рёбра».
- **Почему BINUP, а не Heavy-Light или Euler tour.** BINUP даёт:
  - `O(log N)` на LCA и агрегаты (`max`/`min`) одновременно;
  - простую итеративную реализацию без рекурсии в запросе;
  - лёгкое расширение таблиц (добавить агрегат — добавить массив).
  Heavy-Light быстрее константно, но сложнее и не даёт агрегаты бесплатно.
- **Почему два запроса — `max` и `min`.** Это разные вопросы:
  - `query_path_binup` отвечает «какой максимальный вес на пути» — верхняя
    оценка, которую печатает AST (`path_max_weight`);
  - `query_path_min_binup` отвечает «какое узкое место» — истинный
    `path_bottleneck`, который не может превышать поток.
  Смешивать их нельзя: минимум — это гарантия, максимум — оценка.
- **Почему reroot пересчитывает DFS.** После смены корня меняются `depth`,
  `up` и агрегаты. Ленивое обновление усложнило бы запросы; полный пересчёт
  на 64 узлах стоит ~2.2 µs и проще для верификации.

## Последствия

- **Выигрыш:** `query_path_binup` — ~22 ns (~45 млн запросов/с); `reroot` —
  ~2.2 µs (~450 тыс. операций/с); путь и поток согласованы, потому что
  используют один набор рёбер.
- **Цена:** `reroot` — `O(n log n)` и не подходит для частой смены корня в
  горячем цикле. Для 64 узлов это приемлемо; для больших графов нужен
  другой механизм (например, link-cut tree).
- **Ограничение:** DSU без union by rank/размера; на 64 узлах это не
  критично, но для больших графов стоит добавить эвристику.
- **Ограничение:** `query_path_binup` возвращает максимум, а не сумму;
  потребители должны явно выбирать `min`-версию для bottleneck.
