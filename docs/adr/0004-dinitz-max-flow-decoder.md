# ADR-0004. Поток Диница: zero-allocation кэш-локальный декодер

- **Статус:** Accepted
- **Дата:** 2026-11-19
- **Модуль:** 3.4, `include/dinitz_decoder.hpp`

## Контекст

Морфемная маска должна не только описывать домены, но и **гейтировать**
вычислительный путь: разные запросы должны давать разную пропускную
способность графа мыслей. Нужен алгоритм максимального потока, который:

- работает на графе фиксированного размера (64 вершины, 192 направленные
  дуги в тестовом подграфе);
- не аллоцирует память на каждом запросе;
- детерминирован и пригоден для жёсткого реального времени;
- умеет сбрасываться по новой маске без пересборки графа;
- оставляет след (`flow` на рёбрах), из которого можно извлечь путь.

## Решение

Взят **алгоритм Диница** в плоской реализации:

- ёмкости `MAX_V = 128`, `MAX_E = 1024` — фиксированные `std::array`;
- рёбра хранятся парами `e` и `e^1` (прямое/обратное), у каждой пары есть
  `base_cap` (паспортная ёмкость) и `cap` (текущая);
- `head`, `level`, `ptr`, `q_buf` выровнены по 64 байта;
- `apply_boolean_mask_and_reset(mask)` для каждой пары выставляет
  `cap = base_cap`, если бит `tag` установлен в маске, иначе `0`, и обнуляет
  `flow`; обратное ребро всегда получает `cap = 0`;
- `max_flow` — классический цикл BFS (уровни) + DFS с `ptr` (блокирующий
  поток);
- `extract_optimal_thought_path` идёт по прямым рёбрам с `flow > 0`,
  предпочитая максимальный поток, и не зацикливается благодаря `vis`.

## Обоснование

- **Почему Диниц, а не Эдмондс–Карп.** Эдмондс–Карп на каждом шаге ищет один
  augmenting path BFS; Диниц за одну фазу находит блокирующий поток по
  слоистой сети. На плотном подграфе это меньше фаз и лучше использует
  локальность. Эталон Эдмондса–Карпа оставлен в бенчмарке для проверки
  корректности (`dinitz_matches_edmonds_karp`).
- **Почему фиксированные массивы.** Максимальный поток вызывается на каждом
  запросе. `std::vector` внутри горячего пути давал бы аллокации и
  непредсказуемые паузы. Верхние границы известны из топологии (128 вершин,
  1024 дуги), поэтому выход за лимит — это ошибка конфигурации, а не
  штатный режим (`add_static_edge` просто игнорирует переполнение).
- **Почему `base_cap` + `cap`.** Маска меняется от запроса к запросу, но
  топология постоянна. Хранить «паспортную» ёмкость и восстанавливать её —
  дешевле, чем пересобирать рёбра.
- **Почему `semantic_tag` на ребре.** Это тот же язык, что и кластеры
  морфемного trie. Маска запроса напрямую открывает/закрывает рёбра, поэтому
  `max_flow` становится объяснимой функцией смысла запроса, а не чёрным
  ящиком.
- **Почему путь берётся из `flow`.** После `max_flow` прямое ребро с
  положительным потоком — это ребро, реально участвующее в потоке. Путь
  пригоден для трассировки и AST.

Измерения: сброс по маске + `max_flow` для 64 вершин и 192 дуг — **780 ns**
(~1.28 млн операций/с). Для тестового запроса `max_flow = 259`,
`path_bottleneck = 120`.

## Последствия

- **Выигрыш:** нет аллокаций в горячем пути; задержка предсказуема; маска
  управляет проводимостью без пересборки графа; результат проверяется
  независимой реализацией.
- **Цена:** жёсткие лимиты `MAX_V`/`MAX_E`. Расширение подграфа требует
  изменения констант и пересборки; выход за лимит молча отбрасывает рёбра,
  поэтому конфигурацию нужно валидировать тестом.
- **Ограничение:** `extract_optimal_thought_path` — эвристика по остаточному
  потоку, а не единственный канонический путь. Для AST используется путь в
  остовном дереве (`path_between`), а поток — для величины/ёмкости.
  Это разделение зафиксировано в [ADR-0010](0010-unified-pipeline.md).
- **Сложность:** худший случай Диница — `O(V²E)`, но на фиксированном
  подграфе константы важнее асимптотики.
