# ADR-0013. Предметная верификация против brute-force и контрактные тесты

- **Статус:** Accepted
- **Дата:** 2026-11-19
- **Модули:** `benchmarks/`, `tests/`

## Контекст

Алгоритмы ядра оптимизированы вручную (плоские массивы, фиксированные
ёмкости, эвристики). Ошибка в таком коде легко остаётся незамеченной:
неверный путь, потерянный кластер или лишний домен выглядят правдоподобно.
Нужна проверка, которая:

- сравнивает каждый алгоритм с независимой эталонной реализацией;
- проверяет предметные свойства текста (язык, кластеры, round-trip);
- фиксирует контракт AST и детерминизм;
- запускается локально и в CTest без внешних сервисов.

## Решение

Два уровня проверки.

**1. Логические задачи** (`benchmarks/logic_tasks.py`) — каждый алгоритм
сравнивается с brute-force:

| Задача | Проверяемое свойство |
|---|---|
| `path_matches_bfs` | `path_between` == BFS-путь в MST |
| `path_max_weight_matches_bruteforce` | `query_path_binup` == max вес на пути |
| `path_min_weight_matches_bruteforce` | `query_path_min_binup` == истинный bottleneck |
| `reroot_preserves_paths` | reroot не меняет путь и веса |
| `kruskal_maximum_spanning_tree` | `n−1` рёбер, вес == эталонному Краскалу |
| `dinitz_matches_edmonds_karp` | max-flow == Эдмондс–Карп на случайных графах |
| `centroid_lookup_bounds` | `hops ≤ 4`, глубина `≤ ⌈log₂N⌉ + 1` |
| `trie_known_root_clusters` | известные корни дают ожидаемый кластер |
| `trie_unknown_words_clean` | неизвестные слова не дают ложных кластеров |
| `flow_bottleneck_invariants` | bottleneck ≤ flow, путь root→sink, flow > 0 |

**2. Задачи анализа текста** (`benchmarks/text_tasks.py`):

| Задача | Проверяемое свойство |
|---|---|
| `language_detection` | RU/EN определяется верно |
| `semantic_cluster_detection` | precision/recall/F1 по кластерам |
| `morpheme_segmentation` | ожидаемая основа присутствует |
| `unknown_words_no_clusters` | мусор не создаёт кластеров |
| `nl_round_trip_consistency` | recall ≥ 0.99, отчёт согласован |
| `deterministic_output` | одинаковый вход → одинаковый выход |
| `ast_contract` | маркеры AST и согласованность с `optimal_path` |

**3. Модульные и контрактные тесты** (`tests/`):

- `test_ae_core.cpp` — C++23 ядро и C ABI;
- `test_bindings.py` — Python-обвязка и SLM-мост;
- `test_ae_core.cpp`/`test_features.py` — признаки и датасет;
- `test_graph_training.py` — контракт обучения;
- `test_benchmarks.py` — запуск предметных наборов;
- HIP smoke test регистрируется в CTest при `AE_ENABLE_HIP_TESTS=ON`.

## Обоснование

- **Почему brute-force, а не «золотые» значения.** Эталон, независимо
  реализованный на Python, ловит ошибки в оптимизированном C++ (например,
  перепутанные max/min или неверный reroot). Жёстко зашитые числа быстро
  устаревают и не объясняют, что именно сломалось.
- **Почему предметные задачи, а не только юнит-тесты.** Морфемная маска и
  NL-контур — вероятностные по смыслу; проверять нужно precision/recall,
  а не отдельную функцию.
- **Почему детерминизм — отдельный тест.** Он ловит случайные seed'ы,
  wall-clock в признаках и неупорядоченные обходы, которые иначе проходят
  все остальные проверки.
- **Почему контракт AST.** AST — граница с SLM; если он ссылается на
  несуществующий узел или теряет маркеры, модель получит ложный контекст.
  Тест проверяет и схему, и согласованность с `optimal_path`.
- **Почему всё запускается в CTest.** Единая команда
  `ctest --test-dir build --output-on-failure` делает проверку частью
  сборки, а не отдельным ритуалом.

## Последствия

- **Выигрыш:** текущий результат — **1.000** по обоим наборам (см.
  `reports/benchmarks.json`); регрессии ловятся до попадания в релиз;
  эталоны документируют ожидаемую семантику.
- **Цена:** brute-force растёт быстро; наборы ограничены небольшими
  графами/корпусами, чтобы тесты оставались быстрыми (~0.3 с для CTest).
- **Ограничение:** 1.000 на seed-корпусе не означает 1.000 на произвольном
  тексте; это проверка контракта и отсутствия регрессий, а не оценка
  обобщения.
- **Ограничение:** HIP-проверка — smoke test; она подтверждает компиляцию,
  выделение памяти и dispatch, но не корректность полного обучения на GPU.
